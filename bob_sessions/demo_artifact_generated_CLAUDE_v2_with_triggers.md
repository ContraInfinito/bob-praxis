## Trigger Keywords

When the user's message contains the keyword `design` or `scope` (case-insensitive, anywhere in the message), enter STRICT prompt-first mode. Produce a six-field structured prompt and wait for explicit user approval before any action — even if the request appears clear.

The six fields, in order:

1. **Restated request** — bullet-point reformulation of what you think the user wants
2. **Assumptions** — every assumption you would make if you proceeded as-is
3. **Scope IN** — what is included in the work
4. **Scope OUT** — what is deliberately excluded
5. **Proposed approach** — one or two sentences summarizing your implementation strategy
6. **Open questions** — anything you need clarified before starting

Wait for the developer to approve, edit, or reject the structured prompt. Do not write code, edit files, or run commands until they approve.

Example trigger phrases: "Design a rate limiter", "Scope out the auth system", "Help me design the database schema". Plain questions like "what does this file do?" or "run the tests" do not trigger strict mode.

## Conventions

- Use Flask's application context and request context appropriately; access `request`, `session`, and `g` only within request handlers
- Follow Flask's blueprint pattern for organizing routes when the application grows beyond a single module
- Write pytest fixtures in `conftest.py` for shared test setup; use `app.test_client()` for testing Flask routes
- Pin dependencies with exact versions in requirements.txt (as currently done with `flask==3.0.0`); use virtual environments for isolation
- Structure Flask projects with `app.py` or `__init__.py` at the root; keep route handlers focused and delegate business logic to separate modules
- Use Flask's built-in development server (`app.run(debug=True)`) only for local development; deploy with WSGI servers like Gunicorn or uWSGI
- Test both successful responses and error cases; assert on status codes, response data, and headers as needed


### Flask

- Use blueprints for modular route organization
- Store configuration in environment variables, not hardcoded
- Use Flask's `current_app` for accessing app context
- Test routes using Flask's test client


### pytest

- Use fixtures for test setup and teardown
- Parametrize tests to cover multiple cases
- Use descriptive test names: `test_<function>_<scenario>_<expected>`
- Run tests with: `pytest -v`


## What to avoid

- Don't add credentials, API keys, or tokens to any file. Use environment variables.
- Don't modify build artifacts, generated files, or anything under `.git/`, `venv/`, `__pycache__/`, or `node_modules/`.
- Don't introduce dependencies without explaining why and how they fit the project's scope.
- When in doubt about a design decision, ask before implementing — see the Prompt-first execution principle above.

### Structured Prompt — awaiting your approval

**1. Restated request**

- Add a rate-limiting mechanism to the Flask app in app.py so that callers exceeding a configured request rate receive a 429 Too Many Requests response instead of the normal handler output.
- Cover the existing GET / route, and structure the limiter so it applies cleanly to future routes as well.
- Include pytest coverage in test_app.py (or a new conftest.py) verifying both the allowed-path and the throttled-path behavior.

**2. Assumptions (every assumption I'd make if I proceeded as-is)**

- Scale: single-process, single-host (dev/test). No need for a distributed store (Redis/Memcached).
- Identity: rate-limit by client IP (request.remote_addr), since there is no auth, no API keys, and no user model.
- Algorithm: fixed window counter — simplest correct algorithm; acceptable burst behavior for a toy API. Defined: count requests per key per N-second window; reject when count exceeds limit; reset counter at window boundary.
- Limit: a placeholder of 60 requests per 60 seconds per IP, configurable via env var (RATE_LIMIT_PER_MINUTE) per the Flask convention noted in CLAUDE.md ("Store configuration in environment variables").
- Storage: an in-memory dict guarded by a threading.Lock. No persistence across restarts — acceptable because rate limits are by their nature short-lived.
- Library choice: prefer the standard library over adding Flask-Limiter, because Flask-Limiter pulls limits + (optionally) redis and the Simplicity bias principle favors not adding dependencies for a single endpoint. I'll explicitly call this out in the Open questions — you may prefer the library.
- Response shape: 429 status, plain-text body "Rate limit exceeded", and a Retry-After header (seconds until window reset) so clients behave correctly. Defined: Retry-After is the standard HTTP header (RFC 9110 §10.2.3) telling a client how long to wait before retrying.
- Test strategy: use Flask's test_client() (already pattern in the repo) and exercise the limiter by issuing N+1 requests in a loop within one window; assert the (N+1)th returns 429. Stub the clock or set a very low limit in tests to keep them fast.

- Proper 429 response with Retry-After.

**5. Proposed approach**

Implement a small RateLimiter class with an in-memory dict[ip → (count, window_start_epoch)] protected by a threading.Lock, exposed as either a @limit decorator or a before_request hook registered on the Flask app. On each request: identify the client by request.remote_addr, atomically increment/reset the bucket, and either let the request through or abort(429) with a Retry-After header. Tests inject a tiny limit (e.g., 2/window) and a short window to make the throttling path fast and deterministic.

★ Insight ─────────────────────────────────────

- Why time.monotonic() over time.time(): rate limiters compare elapsed durations, not wall-clock instants. time.monotonic() never goes backward, so a system clock adjustment (NTP slew, DST) cannot accidentally widen or narrow a window. This is a classic correctness footgun in hand-rolled limiters.
- Why a module-level singleton, not an app factory: the project has no factory pattern yet, and adding one just to host a limiter violates Simplicity bias. We pay a small testing cost (need to swap the limiter in fixtures) but avoid restructuring the whole app.
- Why I'm splitting tests into test_rate_limiter.py + test_app.py: the unit tests for the limiter class don't need Flask at all — they're pure data-structure tests. Keeping them Flask-free makes the limiter portable and the tests ~10× faster.

★ Insight ─────────────────────────────────────

- Why max(1, math.ceil(...)): math.ceil(0.0001) == 1, so this only matters in the boundary case where retry_after is exactly 0.0 — which my limiter never returns when blocked (it returns the strictly-positive remaining window). But the cost of being defensive is one extra builtin call, and the cost of being wrong is a client immediately retrying into another 429. Cheap insurance.
- Concurrency test technique: the test fires N threads × M calls at the same key with a tight limit, then asserts the exact allowed count equals the limit. Without the lock, you'd see count > limit (because each thread races between the count < limit check and the count += 1 write). Python's GIL doesn't save you here — the read-modify-write spans many bytecodes.
